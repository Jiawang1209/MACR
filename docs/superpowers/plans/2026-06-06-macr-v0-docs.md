# MACR V0 Documentation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Restructure the single-file MACR blueprint into a clean, bilingual, open-source-ready GitHub repo documentation set (README + `docs/` + `examples/` stubs), faithful to the existing blueprint.

**Architecture:** Pure documentation work, no code. Reference docs (`message_protocol`, `agent_roles`, `workflow_templates`) are written first because other docs link to them; `architecture.md` ties them together; `README.md` is written last as the front door that summarizes and links everything; a final coverage check verifies no blueprint content was lost.

**Tech Stack:** Markdown only. Diagrams as fenced ASCII/`text` blocks (no external image tooling). Bilingual: README 中文在前、英文在后;`docs/` 中文为主、英文术语保留。

**Source of truth:** `MACR_Multi-Agent_Collaborative_Reasoning_Framework.md` (§ = section number). Spec: `docs/superpowers/specs/2026-06-06-macr-v0-docs-design.md`.

**Conventions for every task:**
- "Verify" steps are a content checklist + a markdown link sanity check, not automated tests (this is a docs repo).
- Link check command (run from repo root): `grep -oE '\]\([^)]+\.md[^)]*\)' <file> || echo "no internal links"` — then eyeball that each linked path exists.
- Commit after each file. Keep the original blueprint file untouched (it is the source archive).

### Task 3: `docs/agent_roles.md`

**Files:**
- Create: `docs/agent_roles.md`

Source: §4.1–§4.7 (7 roles), §16.1 (precise-role style principle).

- [ ] **Step 1: Write the file — one subsection per role + a style principle section**

For EACH of the 7 roles, use this uniform 4-field template (职责 / 边界 / 权限 / 消息类型). Content per role comes from the blueprint:

1. **Supervisor / Orchestrator** (§4.1) — 职责:接收/判断/拆解任务,决定调用哪些 Agent、控制执行顺序、维护全局状态、触发审查/返工/人工审核、生成最终输出。边界:不负责专业判断,只负责流程控制与协同调度。权限:读写 Blackboard、路由消息。消息类型:产出 `task`/`decision`,消费全部。
2. **Planner** (§4.2) — 职责:生成初步方案、拆解步骤、判断所需工具/数据、给出执行路线、标记风险。边界:不执行、不评判合格。权限:读 Blackboard。消息类型:产出 `proposal`/`plan`。
3. **Executor / Implementer** (§4.3) — 职责:按明确方案执行,生成代码/分析/报告/图表,记录过程,输出证据(改动文件/工具调用/测试结果)。边界:只基于 approved plan 执行;不决定是否合格。权限:工具调用、写产物。消息类型:产出 `result`/`revision_result`。
4. **Reviewer** (§4.4) — 职责:审查 Planner 方案与 Executor 结果,检查逻辑错误/偏离目标/缺证据,给修改建议。边界:不重新执行任务;默认不能改代码。权限:只读。消息类型:产出 `review`/`critique`/`revision_request`。
5. **Evaluator** (§4.5) — 职责:依据规则/证据/测试结果/指标判断是否合格,判断是否返工/是否人工审核,输出 PASS/NEEDS_FIX/BLOCKED。边界:不执行任务。权限:只读 + 规则库。消息类型:产出 `evaluation`/`decision`。
6. **Tester** (§4.6) — 职责:运行测试、设计用例、验证边界条件、检查可复现性、输出测试日志。边界:不评判最终合格(交 Evaluator)。权限:运行测试工具。消息类型:产出 `test_report`。
7. **Human Gate** (§4.7) — 职责:关键决策最终确认,接收输出,修改/批准/驳回,把人工反馈写回系统,作为最终责任主体。边界:非自动化角色。权限:最高(批准/驳回/合并/发布)。消息类型:产出 `human_feedback`。

**Style principle section** (§16.1): contrast 模糊角色(`你是一个优秀的全栈专家。`)vs 精确角色(代码审查智能体:只能审查 git diff、不改代码、每个问题含文件路径/风险等级/原因/建议)。State the rule: 每个 Agent 必须有明确边界与最小权限。

Add top cross-link: `> 消息格式见 [message_protocol.md](message_protocol.md)。`

Confirm all 7 roles present each with 职责/边界/权限/消息类型, plus the style-principle contrast.
