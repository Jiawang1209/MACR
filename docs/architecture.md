# MACR 架构概览

> 角色见 [agent_roles.md](agent_roles.md);消息格式见 [message_protocol.md](message_protocol.md);工作流见 [workflow_templates.md](workflow_templates.md)。

## 1. 设计哲学(为什么是结构化协同)

多智能体协作不应理解为"多个 AI 在一起随意聊天"。自由聊天的典型问题:Agent 互相迎合;讨论热闹但无有效结论;任务边界模糊;责任不清;中间过程不可追溯;输出无法验证;容易幻觉与过度推断。

MACR 的核心是一套可控的协同推理协议。用以下公式表达:

```text
结构化消息 + 明确角色 + 共享状态 + 任务编排 + 交叉审查 + 人工门控
```

## 2. 框架与应用的关系

MACR 是通用底座,不写死任何具体领域;领域应用在其上配置不同的 Agent、工具、规则与工作流。

```text
MACR = 通用多智能体协同推理底座
软件开发协作系统 = 基于 MACR 的工程应用
农田生态保育决策系统 = 基于 MACR 的领域应用
科研论文智能辅助系统 = 基于 MACR 的科研应用
```

MACR 抽象出的通用机制:Agent、Role、Task、State、Message、Tool、Evidence、Review、Decision、Feedback、Workflow、Human Gate。具体应用示例见 [`examples/`](../examples/)。

## 3. 总体架构与数据流

```text
                ┌─────────────┐
                │  用户 / Task │
                └──────┬──────┘
                       ▼
                ┌─────────────┐        路由 / 编排
                │  Supervisor  │◄───────────────────────┐
                └──────┬──────┘                          │
                       │ 调度                             │
   ┌─────────┬─────────┼─────────┬──────────┐            │
   ▼         ▼         ▼         ▼          ▼            │
┌──────┐ ┌──────┐ ┌────────┐ ┌────────┐ ┌──────┐        │
│Planner│ │Execu-│ │Reviewer│ │Evalua- │ │Tester│        │
│       │ │ tor  │ │        │ │ tor    │ │      │        │
└───┬──┘ └───┬──┘ └────┬───┘ └────┬───┘ └───┬──┘        │
    │        │         │          │         │            │
    └────────┴─────────┴────┬─────┴─────────┘            │
                            ▼                            │
                  ┌───────────────────┐  读/写            │
                  │  Blackboard /      │──────────────────┘
                  │  Shared State      │
                  └─────────┬─────────┘
                            ▼ PASS
                     ┌────────────┐
                     │ Human Gate │ → Final Output
                     └────────────┘
```

所有 Agent 通过中央 Blackboard / Shared State 读写,而非点对点直连;Supervisor 负责路由与编排;Evaluator 在 PASS 时放行;Human Gate 做最终确认并产出 Final Output。

## 4. 关键架构决策

### 通信模式

默认采用 **Blackboard + Supervisor 路由**,而非自由点对点直连——便于追溯、统一状态、降低耦合。

### 时序模式

**回合制**(方案讨论、互审、决策生成)与 **异步**(多工具调用、长任务执行、并行检索)按场景选用。

### 冲突处理

高风险任务**不自动投票决定**,进入 Human Gate;低风险可用 Supervisor 仲裁 / Evaluator 评估 / 规则约束 / 证据优先 / 置信度排序。

## 5. 核心设计原则

1. **角色明确** — 每个 Agent 必须有明确边界,避免模糊角色。
2. **状态显式化** — 输入、计划、执行结果、审查意见、证据、决策、测试日志、人工反馈都写入 State。
3. **证据可追溯** — 所有关键结论都能追溯到数据/文件/文献/代码/工具调用/测试日志/专家规则。
4. **权限最小化** — 每个 Agent 只能访问必要工具(Reviewer 默认不能改代码,Evaluator 默认不能执行任务)。
5. **结构化输出** — Agent 输出尽可能结构化(JSON),而非纯自然语言。
6. **Human-in-the-loop** — 高风险决策、不确定输出、证据不足、多 Agent 冲突、最终合并、对外发布等关键节点必须支持人工确认。
